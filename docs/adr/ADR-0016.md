## 事实与最小复现

Python `DeepSeekProvider` 已有官方 HTTPS 传输、授权检查、usage 和 unknown 分类，要求
受信 durable CallLedger。当前实验中，Go `workerWith` 的 `/v1/models` 仍固定使用
`mockDecision` 与 `demo-free.v1`；`budget.ModelRequest.Valid`、`Pricing.Valid` 只接受
mock。`mgareval` 也只接受 mock，fixture 与 manifest 仅选择 offline/development。
因此提供 key 尚不足以完成 P7-06，真实 Provider 与完整实验层的接通仍未实现。

`evidence/batches/P7-06/provider-boundary-reproduction.log`：构建实际 CLI 后传入
`--provider deepseek --case live-001 --arm B0`，真实退出码 2，输出
`experiment_configuration_denied`。拒绝发生在打开数据库/调用模型之前。
这证明当前门禁在工作，不能据此宣称真实模型评测通过。

检查环境配置得到：无 secret bindings，网络为 restricted，`api.deepseek.com` 不在
effective allowed hosts；未探测官方接口、未发送付费请求。模型仍待用户选择。

## 建议：三张依赖顺序子卡

- P7-06A：可信 Provider 传输与真实 PG 预留/结算接入，先只使用本地 HTTP 故障服务器。
  Go broker 持有密钥；Python Agent 继续使用现有受控本地模型入口。配置固定 Provider、
  模型、价格版本和上下文/输出上界；每次发送前成功持久化预留。已发但结果不确定时保留
  上界、停止自动重放；缺 usage 不补零。模型文本仍不授予自身工具或验证权限。
- P7-06B：将已验收传输接入 B0/B1/B2/B4 与 live manifest，冻结 96 个分配项及总预算。
  用 development 集和本地故障服务器验证闭环、缺配置拒绝、重复启动与未知结果保护；
  不用 holdout 的真实模型结果调 Prompt。不发真实请求。
- P7-06C：模型、密钥、官方单价版本、网络和费用上限全部明确且用户显式授权后，执行
  冻结 24 题 × 4 组，对账与外部 Oracle 评价。预算耗尽等失败保留，未执行项 NOT_RUN。
  P7-06 父卡只有 C 验收后才可 PASS。

生产文件预计横跨预算类型、Provider 传输、模型 broker、fixture、严格/基线执行配置、
CLI、live runner 和启动脚本；合并在一张卡将超过约八个生产文件。三张卡各自先失败后
通过并保存真实回归。复用现有 model_calls/run_budgets，当前提案不新增 DDL；若需要
迁移或改变 unknown 重放语义，另提交明确设计，不自行执行。

## 总费用与公平性提案

`eval/live/plan.json` 给出 96 个明确分配项，每项目前 NOT_RUN。三种难度各八题，
incident/analysis 各十二题，六个拒绝负例。初始四组之外的 B3/A1/A2 明确 NOT_RUN。

总美元上限由用户给定，不设置默认值。建议先把该上限以整数微美元等分为 96 份，
每份不超过冻结 case 的 $1 上限，所有份额之和不超过用户上限；所有组同题同上限。
每份绑定不可变 assignment/run 身份，禁止重复启动分配新的费用份额；未知结果占用
原份额，崩溃重启拒绝自动重跑；初版不转移题目间剩余额度。此策略偏保守，但无需
新增全局预算表。实现时必须用跨进程重复启动、超额预留和崩溃恢复验证。

6144 请求、6291456 tokens、$96 是现有冻结限额推得的理论总上界，**不是费用估计或
授权额度**。实际允许费用还受更低的用户总上限约束。报价未核实，所以预计费用是 N/A。
供应商未承诺稳定版本的模型别名须如实记录请求/响应模型标识和时间，不能声称精确模型
版本锁定。最终报告区分 Provider usage、按冻结单价估算和供应商实际账单。
