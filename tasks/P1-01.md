# P1-01 · 数据库迁移与状态机 Schema

> **阶段：P1 — 持久化工作流与 DAG**  
> **依赖：P0-03**  
> **执行粒度：仅本卡；完成后停止并交回人工验收**

## 本卡目标

建立精确的持久化模式和可回滚的测试数据库。

## 允许修改的主要文件/模块

`migrations/001_control.sql, internal/store/schema.go, tests/integration/schema_test.go`

如确需新增测试/小型辅助模块，可在本卡范围内增加；若涉及未批准的持久化协议修改或跨阶段大量重构，停止并提交 CHANGE_REQUEST。

## 开发步骤与设计要求

按 02 文档创建 Workflow, orchestrator_leases, plans, nodes, edges, tasks, outbox/inbox, artifact, budgets, model/tool ledger, events；完成 UNIQUE/CHECK/FK/终态及基础索引；迁移按序执行，预留独立角色。

必须遵守 `02_ARCHITECTURE_CONTRACTS.md` 对身份、状态、预算和版本的约束；LLM 不能直接更新权威状态，所有新写路径均有真实测试和审计。

## 正向验收（必须自动化）

新 DB 完整迁移；已迁移再次执行不重复；Schema assertion 校验关键列、索引、FK、check。

## 反向验收 / 故障或越界（必须自动化）

非法 role、非法 FK、重复 event idempotency key、负预算值必须由 DB 层拒绝；迁移失败回滚不留半成品。

## 本卡验收命令

```bash
bash scripts/bootstrap.sh --fresh-test-db && go test ./internal/store/... ./tests/integration/...
```

命令中的脚本/测试路径属于应交付接口；如仓库尚无该脚本，先在本卡实现所需脚本或等价测试入口并更新说明。Codex 必须记录真实运行的命令及退出码，不得仅复制上述命令假装执行。

## 交付清单与停止条件

- [ ] 仅本卡功能完成，相关测试先失败后通过（适用时）
- [ ] 正向/反向断言通过，未通过项原样保留
- [ ] Go/Python 已存在的全量回归未退化（无法运行说明原因）
- [ ] 写出 `evidence/batches/P1-01/accept.json` 和相关日志，注明 commit/未提交状态
- [ ] 在 `TASK_QUEUE.md` 标记真实状态，简述已知边界，向用户交付结果并**停止**

**不得做的事：** 擅自进入下一任务卡；用 Mock 数据伪装真实模型实验；为了 PASS 跳过测试；自行发付费请求；默认执行危险宿主操作。
